## 项目目标

以公开历史零售数据建立一个可解释、可复现的商品分析作品，回答商品组合、销量变化、需求预测、价格关联和购物行为等问题。使用独立数据集补充不同业务视角，保留各自的来源、粒度与限制。不同公司的商品或用户编号不做跨数据集关联，也不汇成一个虚构企业的经营结果。

这个项目延续银行项目的顺序：业务问题 → 来源和口径核验 → 原始层 → 类型化清洗 → 分析模型 → SQL/统计分析 → Power BI → 结论、验收与 GitHub 展示。

## 数据模块与边界

| 模块 | 计划使用 | 重点问题 | 必须保留的解释边界 |
|---|---|---|---|
| 核心：M5 | 商品、门店、历史日销量、日历及价格 | 商品组合、ABC/XYZ、28 天销量预测、价格与销量关联、异常排查 | 观测销量不等于未受供给约束的真实需求；零销量不能直接判定缺货。价格与销量关系不自动代表因果效果。没有成本或库存时不计算利润、库存周转或实际补货收益。 |
| 独立补充：Retailrocket | 行为事件及商品信息 | RF 行为分群、购物篮组合、可定义的浏览至购买路径 | 根据字段审计确定会话与购物篮口径；事件次数不等于独立人数或订单数。没有可核实金额时不称为货币 RFM。漏斗受事件覆盖和会话定义影响。 |
| 可选：Criteo corrected v2 | 经来源核实的实验数据 | 随机分组、处理效果和 uplift 方法 | 仅在核实 corrected v2、分组机制、结果定义及适用分析条件后开展；不能把其他数据集的商品建议包装成已经验证的干预效果。 |
| 可选：Complete Journey | 经来源核实的交易与促销字段 | 货币 RFM、优惠券及促销关联 | 下载、许可和字段覆盖均待核验；观察性促销比较与实验效果分开描述，不把它与 M5 或 Retailrocket 的用户、商品直接连接。 |

前两个模块构成主要学习路线。两个可选模块不作为核心阶段的前置条件，也不提前写入已完成能力。

## 共同工作方式

1. 每次只完成一个可核对的小动作：先说明目的、输入和预期结果，再由你操作。
2. 你提供实际输出后，一起核验、解释和修正；通过后更新进度，再进入下一步。
3. 将“助手独立验证”“用户实际操作”“计划中的步骤”分别记录，不相互替代。
4. 每个已完成的小模块先检查改动和文件清单，再提交并上传；若使用阶段分支和 PR，保留验收说明后再合并。
5. GitHub 的 README、英文来源说明、字段字典、运行指南及阶段提交说明使用英文；中文保留数据集比较、学习讲解与进度记录。
6. 原始大文件、数据库、环境、凭据和用户级明细不进入 Git；公开保存代码、来源获取方式、校验值、质量结果、可公开汇总及报告截图。
7. 观察、推断、建议和已验证效果分开写。历史公开数据分析不能描述为在宜家任职、接入宜家内部系统或已经创造实际商业收益。
