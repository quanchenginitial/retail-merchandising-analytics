# 当前一步：比较两个基线在开发验证期的预测误差

更新日期：2026-10-29（Australia/Sydney）。

**这一步为了什么：把已经保存的两个基线预测，与三个开发验证窗口中的实际销量逐日对照，比较预测有多偏、整体偏高还是偏低。** 这使项目从“正确生成预测”进入“有证据地评估方法”。

SQL35 的 **4 行、12 列全部 PASS**，已与独立预检指纹匹配。WEEKDAY4 四个起点的预测总量为 **8,336、8,891、9,456、8,017 件**，分别等于历史 28 天总销量。零预测记录数为 **1,228、1,168、1,292、1,228**；小数预测记录数为 **3,984、3,956、3,788、3,828**。这些是生成与保存检查通过的证据，还不代表预测更准确。

## 比较范围

沿用 FOODS_1 / CA_1 的全部 **216 个商品序列**，比较两个已保存的方法：

- **SNAIVE7**：重复最近七天的销量模式。
- **WEEKDAY4**：重复过去四次同星期几销量的平均值，保留小数。

评分仅包含 DEVELOPMENT_1、DEVELOPMENT_2、DEVELOPMENT_3，每个窗口为 28 天。每个“窗口 × 方法”都有 **216 × 28 = 6,048** 个预测与实际销量的对应位置，合计 **36,288** 条误差记录。两个方法使用同一批 **18,144** 条实际观察；不是新增了 36,288 条真实销量记录。

最终留出期 **2016-04-25 至 2016-05-22** 继续保留，本步不读取它的实际销量、不计算其误差，也不据此挑选模型。

## 三个指标怎么读

| 指标 | 用途 |
| --- | --- |
| mae | 平均每个商品门店每天，预测与实际销量相差多少件；越低越好。 |
| mean_error | 平均的“预测 − 实际”；正数表示整体高估，负数表示整体低估。正负误差可能抵消，接近零不等于准确。 |
| macro_rmsse | 先用每个商品自身的历史销量变化幅度缩放其预测误差，再对有定义的商品评分取等权平均；在相同范围与规则下越低越好。它不是百分比。 |

RMSSE 的历史尺度，从截至各起点（含当日）的第一个正销量日开始计算，保留其后的零销量。没有足够历史变化时，RMSSE 保持 NULL，并计入 `rmsse_undefined_series`；这些商品仍参与 MAE 和平均误差。`rmsse_valid_series + rmsse_undefined_series` 应等于 **216**。

这一步采用等权平均的 RMSSE，不是 M5 官方按层级和销售额加权的 WRMSSE。要直接比较两个方法的开发误差，不能把 RMSSE 小于 1 自动解释为优于本项目的 SNAIVE7。

## 六行结果的结构

| 字段 | 含义 |
| --- | --- |
| origin / model | 三个开发起点各两行，依次为 SNAIVE7、WEEKDAY4 |
| series_count | 商品序列数，应为 216 |
| evaluated_rows | 参与评分的位置数，应为 6,048 |
| actual_units / predicted_units | 本窗口实际销量总量与预测总量；同一起点两个方法的 actual_units 应一致 |
| mae / mean_error | 全部 216 个序列的平均绝对误差与有符号平均误差 |
| rmsse_valid_series / rmsse_undefined_series | RMSSE 有定义与无定义的序列数 |
| macro_rmsse | 对有效序列逐个算 RMSSE 后的平均分 |
| check_status | 来源、保存的预测、配对和指标检查通过时为 PASS；不表示模型表现优秀 |

每个开发窗口单独汇报，没有混合三个窗口的 TOTAL 行。结果只能支持本次固定试点范围的判断；模型选择和扩大评估范围仍是后续工作。
