## 案例如何选

在突然归零、明显增加、明显减少三类中，分别把所有候选按**相对历史均值的绝对件数差从小到大排序**，取中间的一条。偶数条时取两个中间位置中较前的一条；差值相同则依次按商品编码、门店编码和目标周编号排序，保证重复执行结果一致。

| 案例标记 | 类别 | 候选池位置数 | 选取排名 |
| --- | --- | ---: | ---: |
| CASE_1 | SUDDEN_ZERO | 902 | 451 |
| CASE_2 | LARGE_INCREASE | 6,118 | 3,059 |
| CASE_3 | LARGE_DECREASE | 5,327 | 2,664 |

排序单位是“商品门店周”，同一组合的不同候选周都保留；若同一组合被两个类别选中，也不人为替换。选取范围包含八个目标周，不只选择候选最多的一周。

这三条是**件数偏离幅度居中的讲解案例**，不是随机样本，也不能代表所有候选。排名比较了整个八周窗口，因此这是回顾性选例，不能当作当时在线检测的结果。CASE 标记用于阅读，不构成数据匿名化保证。

## 怎样读十二列

| 字段 | 含义 |
| --- | --- |
| case_id / selected_class | 案例标记及当初选中目标的类别；同一案例十二行保持不变 |
| retail_week / week_start | 当前展示行的周编号与周开始日期 |
| relative_week | 当前展示周与选中目标周之差；0 表示选中的目标周 |
| units | 当前展示周的实际销量，单位为件 |
| rolling_baseline_units | 当前展示行自己的此前四周均值；最初四周历史不足，显示 NULL |
| screen_class | 当前展示行自己的筛查标签；最初四周显示 WARMUP，后八周按原规则判断 |
| context_role | 该行相对于选中目标所处的位置，见下表 |
| sell_price / has_price | 当前周价格及是否有价；缺价保留 NULL，不补零，不参与筛选 |
| check_status | 选择、来源、时间范围、历史窗口及输出对账是否通过 |

| context_role | relative_week | 读法 |
| --- | --- | --- |
| EARLIER | 小于 −4 | 更早的背景，未进入选中目标的四周参考 |
| BASELINE | −4 至 −1 | 选中目标实际引用的四个历史周 |
| TARGET | 0 | 本次选择复核的候选周 |
| LATER | 大于 0 | 事后观察，只作回顾性背景 |

每个案例恰有四行 BASELINE 和一行 TARGET。**TARGET 行的 rolling_baseline_units 应等于四行 BASELINE 的 units 平均值。**其他行的 rolling_baseline_units 属于各自当时的四周窗口，不是重复使用目标周的参考值。最初四周虽显示 WARMUP，实际销量仍可以成为较后目标的 BASELINE。

完整展示范围固定为 2016-01-30 至 2016-04-22。若目标位于最后一周，就没有 LATER 行；不会补造窗口外数据。事后走势不用于选中目标当时的基线或标签。

## 这一步要回答的问题

先找到 TARGET，再用四行 BASELINE 手工核对均值与类别条件；随后观察更早和更晚的实际走势，判断“暂时变化”“持续变化”等是否只是待验证的解释。价格仅提供背景，不能单凭同时变化建立因果。

具体原因仍需库存、在售状态、促销曝光、补货和交易记录等证据。三个案例不能估计识别准确率、缺货次数或损失金额。见 [案例协议](ANOMALY_CASE_HISTORIES_PROTOCOL.md) 和 [独立验证说明](ANOMALY_CASE_HISTORIES_VALIDATION.md)。
