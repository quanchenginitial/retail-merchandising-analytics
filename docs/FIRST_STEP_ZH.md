SQL33 截图的 **4 行、13 列全部 PASS**，已与独立预检指纹匹配。分析范围保持 FOODS_1 部门、CA_1 门店的全部 **216 个商品序列**，四个预测起点及各自未来 28 天均不变。

## 这次的方法是什么

假设站在某个训练截止日，每件商品都已有最近七天的实际销量。把这七个值按日期顺序重复四遍，就是未来 28 天的预测。这通常称为按周重复的季节朴素法，本项目记作 **SNAIVE7**。这里的七天包括截止日，按日历连续取七天，不是之前 XYZ 使用的“周六至周五”完整零售周。

例如，假设上一周星期一卖了 3 件，未来四个星期一都预测 3 件。这是演示例子，不是某件实际商品的结果。若某个输入日销量为零，对应的未来四个日期也预测零；这些记录仍然保留。

第二周到第四周不能使用预测区间内后来发生的实际销量。我们是在同一个起点一次给出未来 28 天的预测，而不是每天看到新销量后重新预测。

## 四行结果怎么读

| 字段 | 含义 |
| --- | --- |
| origin | 三次开发验证起点，或最终留出期起点 |
| dept_id / store_id | 固定的部门和门店 |
| series_count | 本次参与预测的商品序列数，应为 216 |
| forecast_rows | 该起点生成的预测记录数，应为 6,048 |
| forecast_start / forecast_end | 预测覆盖的 28 天起止日期 |
| last7_units | 全部 216 个商品截至各自截止日（含当日）的最后七天实际销量合计 |
| predicted_units | 该起点未来 28 天的预测销量合计 |
| zero_forecast_rows | 预测值为零的记录数，不是零销量商品个数 |
| check_status | 输入、完整性、来源日期及预测值检查通过时为 PASS |

可以手工核对任意一行：**predicted_units = last7_units × 4**。因为同一周被重复了四遍，这个等式应当成立。这是汇总层面的核对；逐条重复是否正确，还要检查来源日期和预测值，也不能由此证明预测准确。

每个起点只使用该起点之前的数据。早期开发验证区间会成为较晚起点的训练历史，这是正常的时间推进。最终留出期那一行现在只是这个基线的候选预测，本次没有读取该区间实际销量或评价其预测误差，也尚未选择最终模型。

## 后续如何判断好不好

这种方法能保留一周内的销量差异，但没有显式建模增长趋势、节假日或促销。以后会与“过去四次相同星期几的销量平均值”等方法比较，用开发验证期的实际误差判断表现。不能因为这次全部 PASS 就认为模型已经准确或带来了业务收益。

助手独立预检已通过：**24,192 条预测的全部 13 个字段**、413,208 条训练记录的六个字段均与独立来源计算一致，**19 个针对性用例**通过。预检使用独立临时库，来源文件未改动，临时数据已清理。
