**这一步为了什么：为已经完成的“重复最后七天”基线增加一个固定对照，观察使用四周历史平均值后产生的预测。** 先把两个方法都正确构建好，再用同样的实际数据和误差指标比较表现。

SQL34 的 **4 行、11 列全部 PASS**，已与独立预检指纹匹配。SNAIVE7 的四个预测总量为 8,268、8,112、11,368、8,808 件。它们是模型输出，不代表已验证的未来实际销量。

## 新方法怎么计算

沿用 FOODS_1 / CA_1 的全部 **216 个商品序列**、同样四个预测起点和 28 天预测窗口。这次称为 **WEEKDAY4**。

对每件商品，分别找出截至预测起点的最近四个星期一、四个星期二，依此类推，计算每个星期几的平均销量。把这七个平均值重复四遍，得到未来 28 天的预测。

演示例子：过去四个星期一从早到晚分别卖了 **0、2、5、6 件**。

- SQL34 使用最近一次星期一的 **6 件**作为未来每个星期一的预测。
- SQL35 使用四次平均值 **(0+2+5+6)÷4 = 3.25 件**。

这只是演示，不是某件实际商品的结果。零销量也是有效观察，必须参与平均；缺少一天的记录则需要报错，不能自动改成除以三。

3.25 是预测估计，可以保留小数。现在不四舍五入成整数，避免改变后续误差评估。所有输入都来自各自起点以前，四周预测期间不会加入后来发生的真实销量。

## 四行结果怎么读

| 字段 | 含义 |
| --- | --- |
| origin | 三次开发验证起点，或最终留出期起点 |
| dept_id / store_id | 固定部门与门店 |
| series_count | 商品序列数，应为 216 |
| forecast_rows | 该起点的预测记录数，应为 6,048 |
| forecast_start / forecast_end | 未来 28 天起止日期 |
| last28_units | 全部商品截至各自截止日（含当日）的最后 28 天实际销量合计 |
| predicted_units | 该起点未来 28 天的预测销量合计 |
| zero_forecast_rows | 值为零的预测记录数 |
| fractional_forecast_rows | 值不是整数的预测记录数 |
| check_status | 输入、来源、数值及保存结果检查通过时为 PASS |

这里“最近 28 天”是包含截止日的连续日历天，不是之前 XYZ 分析的周六至周五零售周。

可以手算一个汇总关系：**predicted_units 应等于 last28_units**。每个星期几的四次销量先除以四取均值，再重复预测四次，因此总量回到历史 28 天总量。这只是必要的汇总核对；每条预测的来源日期和数值仍要逐条检查。

zero_forecast_rows 和 fractional_forecast_rows 都在数“预测记录”，不是不同商品的个数。预测总量相等、更平滑或零预测减少，都不能证明预测误差更小；要等下一步开发验证比较。

最终留出期目前仍只生成候选预测，本步不读取其实际销量或计算误差，也不选择最终模型。

助手独立预检已通过：**24,192 条新预测的全部 15 个字段**与独立计算一致，413,208 条训练记录的六个字段核对一致，上一套 SNAIVE7 的全部预测也已复核并保持不变。**19 个针对性用例**通过，来源文件未改动，临时数据已清理。
